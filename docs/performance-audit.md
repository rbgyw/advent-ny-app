# Аудит производительности gph-advent

Работа выполнена в `chore/audit-fixes` поверх `e0d1569`. Исходная рабочая директория была чистой. Production, база, RLS, RPC и пользовательские данные не изменялись. Нагрузочные запросы к реальному серверу не выполнялись.

## Найденные причины

- Все маршруты импортировались синхронно; первый экран задания, формы, календарная логика и связанные стили попадали в начальный граф загрузки. SDK Supabase и проверка сессии блокировали даже публичную заставку.
- `getUserCalendar` каждый раз вызывал инициализацию, затем последовательно читал назначения, задания и ответы. При возврате из задания календарь перечитывался целиком; после каждого сохранения также загружался весь календарь.
- Store очищал видимый календарь перед каждым запросом. Ответы устаревших запросов фильтровались по версии, но сами чтения не отменялись, одинаковые запросы не объединялись.
- Восемь изображений упаковок имели до 4096 пикселей по стороне и занимали 22,34 МБ при размере карточки около 73 × 101 CSS-пикселя. Рубашка Таро занимала 1,93 МБ. Шрифты поставлялись в TTF, их объявления повторялись в экранах.
- Календарь и два задания проверяли календарную дату через интервалы каждые 30–60 секунд. Форматтеры `Intl.DateTimeFormat` создавались повторно.
- Предпросмотры вложений скачивались последовательно и повторно даже для неизменённых фотографий.
- Хедеры, состояния загрузки, кнопки и сообщения ошибок повторялись. При старте до монтирования приложения не было содержимого; ошибки загрузки JS оставляли пользователя без понятного восстановления.

## Что изменено

### Сборка и критический путь

Все пять маршрутов и первый экран задания переведены на dynamic import; уже существовавшие асинхронные экраны сохранены. Тяжёлый SDK Supabase загружается при переходе на маршрут, которому нужна авторизация. Guards по-прежнему дожидаются проверки сессии для календаря, заданий и формы входа. Публичные страницы не выполняют запросов Supabase.

Vite использует штатные tree shaking, CSS splitting и modulepreload; добавлен manifest для проверки графа и бюджет начального JS. Ручное дробление vendor-чанков, сторонняя UI-библиотека и массовая предзагрузка заданий не добавлялись. Все runtime-зависимости исходного проекта используются и сохранены.

Уведомлений toast в исходном приложении нет; дополнительная система не создавалась.

### Токены и фоны

`src/tokens.css` содержит палитру, UI/display-шрифты, базовые отступы, скругления, высоту контролов и три повторяющихся градиента: warm, night, task-glow. `src/assets/fonts.css` — единственные объявления двух основных гарнитур. Специальные гарнитуры календаря и отдельных заданий загружаются со своими стилями.

PageLayout централизует тёплый и ночной фон. Общий радиальный градиент использует token; разные геометрические трансформации исходных иллюстраций и уникальные фоны сохранены локально. Media queries оставлены в CSS: custom properties не подставляются в условия `@media` без дополнительного преобразования.

### Загрузка, данные и жизненный цикл

- До запуска Vue виден статический брендированный каркас; ошибка запуска имеет повтор. Короткий индикатор появляется с задержкой 150 мс, операции запускаются немедленно. Искусственных задержек запросов в приложении нет.
- При загрузке маршрута сохраняется текущая страница. Для задания предусмотрен каркас с доступным возвратом. При сохранении сохраняется содержимое и блокируется соответствующее действие.
- Одновременные чтения календаря одного пользователя объединяются, устаревшие чтения отменяются AbortController. Прогресс хранится отдельно по пользователю; смена пользователя синхронно очищает созданный store.
- Повторный вход в календарь использует данные не старше 30 секунд и той же московской даты. Возврат во вкладку, смена даты и ручной повтор выполняют принудительное обновление. Правила доступа по-прежнему обеспечиваются сервером.
- После записи читаются только серверные назначение и ответ соответствующего задания. Отсутствует оптимистическое подтверждение до успешного серверного ответа.
- Ошибка записи привязана к task_id; фоновое обновление не перезаписывает несохранённый текст. Административное редактирование принудительно перечитывает подтверждённые данные.
- Существующие blob URL фотографий переиспользуются; до трёх отсутствующих предпросмотров скачиваются параллельно, удалённые URL освобождаются. Записи и подтверждения Storage остаются последовательными и не отменяются посередине.
- `useCampaignClock` назначает один таймер до следующей полуночи Москвы, при скрытии вкладки снимает его, при возвращении обновляет дату. Таймер обратного отсчёта OTP, необходимый интерфейсу, сохранён с очисткой.
- Анимации CSS приостанавливаются в скрытой вкладке, активные Web Animations приостанавливаются и возобновляются для существующих узлов. Имеющиеся reduced-motion и сценарии анимаций сохранены. Загрузка пар отменяется при закрытии экрана.

### Медиа

25 преобразованных ресурсов: 29 117 370 → 3 618 706 байт. Изображения используют lossless WebP; упаковки имеют максимум 768 × 768, рубашка — максимум 640 × 1055. Содержимое шрифтов не подрезалось: WOFF2 сохранён со всеми глифами, их список проверен при конвертации. SVG-персонажи и детали не изменялись. Аудио шифра сохраняет `preload="none"`; автоматической загрузки видео в календаре нет.

Поэлементные размеры и разрешения находятся в `asset-metrics.json`. Исходные файлы доступны в истории Git. Общие шрифты используют `font-display:swap`; дополнительные preload шрифтов не добавлялись. Конфигурация текущего CDN/хостинга в репозитории отсутствует, поэтому серверные cache headers не менялись. Хешированные `/assets/*` подходят для immutable-кеширования; HTML должен перепроверяться при релизе.

Перекодирование шрифтов и медиа проверено повторными скриншотами; оно может незначительно отличаться субпиксельным сглаживанием.

## Проверки и воспроизводимость

- `npm run typecheck` — TypeScript.
- `npm test -- --reporter=line` — typecheck/build с локальной тестовой конфигурацией, запуск отдельного preview и браузерных тестов.
- `AUDIT_VIEWPORT_WIDTH=1280 AUDIT_VIEWPORT_HEIGHT=900 npm run test:browser -- --reporter=line` — desktop-проверка уже работающего локального preview.
- `npm run metrics` — размеры production-ресурсов и initial JS.
- `AUDIT_BASE_URL=http://127.0.0.1:4173 npm run measure -- /tmp/performance.json` — три холодных запуска заставки, календаря и печенья.
- `AUDIT_BASE_URL=http://127.0.0.1:4173 node scripts/measure-memory.ts /tmp/memory.json` — повторные переходы с замерами JS heap после GC.

Тесты используют локальные ответы Auth, Database и Functions. Отправки настоящих писем, записи в production и нагрузочного тестирования нет. Внешние HTTP-адреса блокируются fixture. Требуется Chromium: можно задать `CHROMIUM_PATH`, использовать `/usr/bin/chromium` или установленный браузер Playwright. Отдельный линтер в проекте не настроен.

## Что требуется проверить с реальным окружением

- Реальная регистрация, доставка и повтор OTP, восстановление/истечение токена, несколько вкладок и пользователей; профиль и действующие роли.
- RLS, доступность по датам, специальные RPC и запрет повторного выбора Таро на сервере. В репозитории нет полного набора реализаций специальных серверных RPC.
- Вложения: reserve/upload/confirm/replace/delete, лимит три файла, истёкшая резервация, сетевой сбой между upload и confirm, административные права.
- Реальная доставка благодарностей и серверная идемпотентность. Содержимое писем в тестах не уходит за пределы локального fixture.
- Chrome Android и Safari iOS на физических слабых устройствах, VoiceOver/TalkBack, экранная клавиатура и длительная игровая сессия.
- Печенье: открытие, анимация, показ пожелания, сбой/повтор сохранения, повторное открытие того же результата, скачивание и системное «Поделиться».
- Кроссворд/пары/Таро/нонограм: закрытие во время перехода или сохранения, повторное открытие, хранение черновиков; два устройства одного пользователя.

Лабораторные метрики не доказывают production LCP/INP или постоянные 60 FPS. Полный INP требует настоящего набора взаимодействий и полевых данных; в отчёте отдельно приводится измеренная длительность тестового взаимодействия. JS heap не равен всей RAM браузера и не включает весь бюджет декодированных изображений/GPU.

## Измеренные результаты

Обе сборки созданы одним toolchain (Node 24.22.1, Vite 8.3.3) с одинаковыми локальными значениями `VITE_SUPABASE_URL=http://127.0.0.1:54321` и фиктивным публичным ключом. Без конфигурации Supabase исходный сборщик удаляет недостижимый код после проверки настроек; такой артефакт не использовался как baseline. Метрики ниже относятся к локальному preview без CDN, gzip или Brotli.

| Production-ресурсы | До | После | Изменение |
| --- | ---: | ---: | ---: |
| Начальный JS в HTML и его статических preload | 422 432 Б | 104 605 Б | −75,2% |
| Все production-файлы, без manifest | 34 579 953 Б | 9 429 926 Б | −72,7% |
| Преобразованные изображения и шрифты | 29 117 370 Б | 3 618 706 Б | −87,6% |

Начальный граф HTML не равен всему JS, который понадобится после dynamic import маршрута. Полные списки чанков и размеры: `performance-baseline.json`, `performance-after.json`. Маршруты загружают нужные им дополнительные чанки.

Лабораторный профиль: Chromium, viewport 393 × 852, CPU ×4, RTT 150 мс, download 200 000 Б/с (1,6 Мбит/с), upload 93 750 Б/с. Auth/Database — локальные fixtures с задержкой 150 мс. По три новых контекста на маршрут; HTTP cache отключён routing. Ниже медианы.

| Маршрут | LCP до → после | CLS до → после | Тестовое взаимодействие, мс | Long Tasks, количество до → после |
| --- | ---: | ---: | ---: | ---: |
| Заставка | 3.896 → 1.444 с | 0.00214 → 0.00214 | 88 → 40 | 3 → 1 |
| Календарь | 9.244 → 3.908 с | 0.00028 → 0.00050 | 64 → 32 | 3 → 2 |
| Печенье | 4.072 → 3.032 с | 0.01466 → 0.01597 | 120 → 96 | 5 → 2 |

Это измеренная длительность одного тестового взаимодействия по Event Timing, а не полный INP. Все CLS ниже 0,1. Цель LCP ≤ 2,5 с достигнута у заставки, но не у календаря (3,908 с) и печенья (3,032 с) на этом профиле. Самая длинная задача календаря: медиана 525 → 498 мс. Осталось ограничение статической иллюстрации из сотен слоёв; стабильные 60 FPS на слабом устройстве этим тестом не доказаны.

Проверена возможность объединить декоративные слои календаря в один вектор. Пробный экспорт через PDF→SVG вырос до 5 445 801 Б; он отвергнут, исходные векторы и детали сохранены. Этот эксперимент не входит в production-код. Следующий обоснованный шаг — компактный вектор непосредственно из исходного макета с отдельной проверкой изображения и серверного сжатия.

| Маршрут | Видимые ResourceTiming entries до → после | Отчётный transfer size до → после | Запросы к backend до → после |
| --- | ---: | ---: | ---: |
| Заставка | 16 → 21 | 2 676 995 → 980 814 Б | 1 → 0 |
| Календарь | 36 → 47 | 2 778 112 → 995 872 Б | 5 → 5 |
| Печенье | 16 → 26 | 2 740 947 → 656 969 Б | 6 → 5 |

Количество ресурсных entries выросло из-за route splitting и переиспользуемых чанков, при этом отчётный объём передачи и LCP уменьшились. ResourceTiming не заменяет полный перехват сетевого трафика: часть preloaded-модулей может показывать нулевые размеры. Backend-запросы посчитаны отдельно fixture и соответствуют фактическим вызовам. На публичной странице устранён запрос сессии для заранее сохранённого пользователя.

Для сохранения число backend-запросов изменилось с 5 до 3: запись + два параллельных чтения одного задания. Быстрый возврат в календарь — 4 → 0 запросов при возрасте данных до 30 секунд; принудительное обновление — 4 → 3. Первоначальная загрузка календаря сохраняет 5 запросов с учётом Auth, но независимые чтения выполняются параллельно.

### Память

Отдельный последовательный прогон: шесть разных экранов для прогрева, затем ещё 12 и ещё 12 открытий; после каждого этапа выполнен GC. Это JS heap, не вся RAM Chrome/изображений/GPU.

| Открытия | JS heap до | JS heap после | DOM nodes до / после | Event listeners до / после |
| --- | ---: | ---: | ---: | ---: |
| 6 | 4 852 068 Б | 5 240 660 Б | 4592 / 5736 | 65 / 107 |
| 18 | 5 397 420 Б | 5 937 072 Б | 4689 / 5736 | 65 / 107 |
| 30 | 5 535 084 Б | 6 051 688 Б | 4592 / 5736 | 65 / 107 |

Общие компоненты увеличили абсолютный JS heap примерно на 0,52 МБ к тридцатому открытию и число DOM nodes/listeners. После изменений nodes и listeners не растут между этапами. JS heap продолжает немного меняться: на последнем этапе +0,115 МБ, исходно +0,138 МБ. Это ограниченный лабораторный прогон, он не доказывает отсутствие утечек в любой длительной сессии.
