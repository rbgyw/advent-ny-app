После перехода на `/calendar` данные были получены, но календарь оставался скрытым и отображалась глобальная ошибка «Не удалось загрузить экран…». Отдельный повторный HTTP-запрос к этому SVG вернул 200: постоянное отсутствие файла не установлено. Источник временного 503 (хостинг или промежуточная сеть) не установлен.
3. **Неверная обработка отсутствующей статики на production.** Проверочные, намеренно несуществующие `/assets/missing-screen-aBcDe123.js` и `.svg` вернули **200 text/html** с SPA-документом. Это не URL из исходных скриншотов и не доказательство отсутствия конкретного рабочего чанка. Но такая конфигурация маскирует пропавшие модули и вызывает ошибки MIME/импорта/декодирования вместо диагностируемого 404. `public/.htaccess` в main уже содержит исключения для статики; production пока не демонстрирует их действие.
4. **HTML не задаёт Cache-Control на production.** Проверены `/`, `/calendar`, `/auth`, `/task/4`. Браузер/прокси может повторно использовать старый HTML; сам по себе этот факт не доказывает, что именно кэш вызвал исходный инцидент.
5. **В JSON лежат ссылки на отсутствующие примерные медиа.** `public/collections/memories.json`, `movies.json`, `videos.json` ссылаются на `collections/images/memory.jpg`, `movie.jpg`, `video-01.jpg`…`video-04.jpg`, `collections/videos/video-01.mp4`…`video-04.mp4`. Этих файлов нет ни в public, ни в dist. Относительные ссылки разрешаются относительно JSON, а не корня домена. Это воспроизводимые отсутствующие ресурсы заданий 22–24, а не установленная причина сбоя календаря. Содержимое подборок оставлено автору; экраны используют локальные заглушки.

Точные URL первоначальных 404 из пользовательских скриншотов неизвестны. Не установлена постоянная потеря какого-либо импортируемого ресурса календаря или ошибка Supabase. Тестовый домен не указан и напрямую не проверялся.

## Новый механизм

Boundary ждёт только track-процессы первоначальных данных и загрузки компонентов, затем следующий Vue tick. Никакие `fonts.ready`, `decode`, CSS-фон или requestAnimationFrame не входят в это условие. Ошибка API отображается существующим состоянием соответствующего экрана; ошибка исполнения/навигации обрабатывается отдельно.

После готовности запускается отменяемое наблюдение ресурсов. У видимых изображений проверяются load/decode с ограничением 4 секунды; offscreen и lazy изображения не форсируются. Поздние load/error и замена src также обрабатываются. Для декоративных img применяется прозрачный fallback, для информативных — штатная светлая подложка/alt; у заголовка календаря уже есть текстовая замена. У фонов остаётся цвет/градиент. Проверяются background/border/mask, ::before, ::after и ::backdrop открытого dialog. Ошибки и задержки фактически загружаемых шрифтов журналируются, текст использует системный fallback.

Диагностика: `[advent] optional|critical <kind> <load|decode|timeout|unexpected>: <safe URL>`. Используется существующий `resource-diagnostics.ts`: для хешированных same-origin ресурсов сохраняется URL без query, fragment и credentials; пользовательские Storage-пути, внешние/inline URL редактируются. Сырые исключения, токены, пароли, ответы Auth и данные пользователя не выводятся.

## Ограничения перед согласованной публикацией

- Исправление ещё не опубликовано. Требуется отдельное подтверждение пользователя на production deploy; workflow остаётся исключительно workflow_dispatch.
- SpaceWeb должен поддерживать OpenSSH `posix-rename@openssh.com`. При отсутствии расширения публикация завершается ошибкой до замены index, без опасного remove+rename. Это проверено имитацией SFTP; запись на production не выполнялась.
- SpaceWeb должен применять .htaccess с mod_rewrite/mod_headers. Поведение проверено на Apache 2.4.71; после разрешённого deploy нужно повторить HTTP-проверки production и auth/calendar с реальной сессией.
- Отсутствующие примерные медиа JSON необходимо добавить по перечисленным путям или заменить ссылки на реальные. Это редакционное содержимое не подменяется выдуманными файлами.
- Старые хешированные ресурсы намеренно не удаляются; их безопасную очистку по сроку жизни вкладок следует планировать отдельно.
- Локальные E2E используют фиктивный backend. Production проверялся только чтением статических файлов и браузерным запуском с подменой Auth/REST; реальная авторизация пользователя не выполнялась.
