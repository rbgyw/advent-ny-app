# Праздничная почта — Yandex Cloud Postbox

Задание 8 вызывает `supabase.functions.invoke('send-gratitude')`. Контракт прежний:

```json
{
  "taskId": 8,
  "requestId": "20000000-0000-4000-8000-000000000001",
  "anonymous": false,
  "senderName": "Иван Иванов",
  "recipient": "colleague@geropharm.com",
  "message": "Спасибо за помощь!"
}
```

`taskId` — фактический ID задания со slug `task-08`, а `requestId` — UUID v4, который клиент повторно использует для неизменённого письма. Успех — `{ "sent": true }`; ошибка — `{ "error": "..." }` с HTTP-статусом. Попап и механика задания не изменены.

`sent: true` означает, что Postbox **принял** письмо и прогресс `{ "sent": true }` сохранён через существующий `save_task_progress`. Это не подтверждение доставки. Журнал хранит состояние `accepted` и `MessageId`, но никогда не устанавливает `delivered`. Доставка, bounce и complaints проверяются отдельно по событиям/логам Postbox; обработчик таких событий в эту замену провайдера не входит.

## Настройка Postbox и секретов

1. Создайте/проверьте адрес для домена `geropharm-advent.ru` в Postbox, подтвердите владение доменом и настройте DNS-записи DKIM, SPF и DMARC согласно подсказкам сервиса. Разрешите отправку от `ded-moroz@geropharm-advent.ru`, если используется список разрешённых отправителей.
2. Сервисный аккаунт должен находиться в том же каталоге, что и адрес, и иметь роль `postbox.sender`. Создайте **статический ключ доступа** (ID и секрет), подходящий для AWS Signature V4; SMTP-пароль или IAM-токен сюда не подставляются. Проверьте доступные квоты и ограничения аккаунта.
3. Задайте в Supabase Dashboard → Edge Functions → Secrets или через CLI следующие серверные переменные:

```dotenv
POSTBOX_ACCESS_KEY_ID=<идентификатор-статического-ключа>
POSTBOX_SECRET_ACCESS_KEY=<секрет-статического-ключа>
POSTBOX_REGION=ru-central1
POSTBOX_ENDPOINT=https://postbox.cloud.yandex.net
POSTBOX_FROM_EMAIL=ded-moroz@geropharm-advent.ru
APP_ORIGIN=https://адрес-приложения.ru
```

`APP_ORIGIN` — точный origin приложения, без пути и завершающего `/`; локально задайте `http://localhost:5173`. Регион, endpoint и адрес имеют указанные значения по умолчанию и проверяются на соответствие этому подключению. Другие адреса/хосты отклоняются до отправки. Имя отправителя — `Дед Мороз` (UTF-8, MIME encoded-word); `Reply-To` — `ded-moroz@geropharm-advent.ru`.

Supabase предоставляет `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` в Edge runtime. Service role используется **только** для закрытых RPC журнала; проверка пользователя, чтение заданий и сохранение прогресса используют пользовательский JWT и RLS. При отсутствии журнала или обязательной конфигурации отправка запрещена.

Секреты хранятся только на сервере. Не добавляйте их в Git, `.env.example`, `VITE_*`, фронтенд или логи. Файл с настоящими секретами для CLI храните вне репозитория. Старые `RESEND_API_KEY` и `GRATITUDE_FROM` функция больше не использует; удаляйте их только убедившись, что другие функции в проекте от них не зависят.

## Развёртывание вручную

Из корня репозитория, после проверки в тестовом Supabase-проекте:

```bash
# Если локальный проект Supabase ещё не инициализирован:
supabase init
supabase link --project-ref "$PROJECT_REF"

# Сверьте историю миграций: сначала должна применяться 013_gratitude_send_journal.sql.
supabase db push --linked --dry-run
supabase db push --linked

supabase secrets set --project-ref "$PROJECT_REF" --env-file /secure/path/postbox.env
supabase functions deploy send-gratitude --project-ref "$PROJECT_REF" --no-verify-jwt
```

`supabase init` нужен только при отсутствии `supabase/config.toml`. Если прежняя схема устанавливалась вручную и история миграций CLI не синхронизирована, не запускайте все старые миграции повторно. Вместо `db push` примените **только новую миграцию 013** транзакцией через SQL Editor либо из терминала:

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 --single-transaction \
  -f supabase/migrations/013_gratitude_send_journal.sql
```

Сначала миграция, затем секреты и функция. `--no-verify-jwt` сохраняет существующий способ работы: старый gateway не проверяет JWT, а обработчик обязательно проверяет его через `/auth/v1/user` **до** резервирования/отправки. Это не отключает авторизацию в обработчике. Настройки OTP и шаблоны Supabase Auth менять не нужно.

При переключении остановите приём новых запросов старой версией и дождитесь её текущих отправок. Защита журнала действует для отправок новой версии: прежний Resend не оставлял в БД ни request ID, ни хеш письма, поэтому восстановить дедупликацию старых отправок из `{ "sent": true }` невозможно. Старые неопределённые отправки нужно сверить с Resend перед повтором через нового провайдера.

Автоматического production deploy этой функции нет. После ручного развёртывания можно отдельно согласовать контрольное письмо на разрешённый корпоративный адрес; автоматические тесты реальные письма не отправляют.

## Отправка, повторы и ограничения

- Проверяются JWT через Supabase Auth, подтверждённый корпоративный адрес автора, активное назначенное задание `task-08` и наступление даты открытия. `user_id` берётся только из проверенной сессии. CORS допускает только `APP_ORIGIN`; отсутствие Origin не заменяет JWT.
- Получатель — только `@geropharm.com`, текст — до 5000 символов, имя — до 120. Имя обязательно для неанонимного письма; в анонимном оно игнорируется. Размер входящего тела ограничен 16 000 байт при чтении потока. Пользовательские значения не попадают в заголовки, `From` или `Reply-To`.
- До обращения к Postbox закрытый RPC `reserve_gratitude_send` атомарно создаёт `pending` в `public.gratitude_sends`. Клиентские роли не могут читать/изменять журнал или вызывать его RPC. Под одной блокировкой проверяются ключ `(user_id, request_id)`, SHA-256 нормализованного письма и лимиты. Хеш включает задание, получателя, текст и выбранную подпись; само письмо и адреса в журнал не сохраняются.
- На пользователя разрешена одна **новая попытка** в 60 секунд, не более 5 за скользящий час и 20 за 24 часа. Явные отказы сервиса тоже расходуют лимит. Проверки существующей отправки лимит не расходуют.
- Тот же request ID с другим содержимым даёт `409`. Тот же текст, получатель и подпись с новым UUID также не отправляются повторно, если предыдущий результат `pending`, `unknown` или `accepted`. Эта защита не истекает через 24 часа.
- `accepted` позволяет повторить только сохранение прогресса. Сбой `save_task_progress` после отправки не вызывает новое письмо. Флаг задания означает выполненное действие, а не доставку.
- Явные отказы 400/401/403/404/413/422/429 записываются как `rejected`; превышение квоты/лимита возвращает `429`, остальные отказы — `502`. Повтор того же запроса возвращает сохранённый отказ. После устранения причины можно вручную создать новый request ID (например, заново открыв задание); лимиты остаются в силе. Нет фоновых или автоматических повторов.
- Таймаут, сетевой сбой, 5xx, redirect, некорректный ответ или успех без непустого `MessageId` дают `unknown` и `409`; прогресс не сохраняется. Таймаут Postbox — 10 секунд, Auth/REST — 8 секунд. HTTP redirect запрещён. Используется один подписанный `POST /v2/email/outbound-emails`, service `ses`, region `ru-central1`.
- Если запись результата не удалась или процесс завершился после резервирования, остаётся `pending`. Ни перезапуск, ни повтор, ни смена UUID, ни истечение времени не освобождают такую запись автоматически. Ошибки БД возвращают `503` и не разрешают отправку в обход журнала.

Из-за отсутствия ключа идемпотентности в SESv2 нельзя атомарно связать принятие письма провайдером с транзакцией БД. Выбран безопасный режим: при неопределённости возможна блокировка письма, которое фактически ещё не было отправлено. Гарантировать одновременно доставку и отсутствие дублей при потере ответа нельзя.

## Разбор неопределённого результата

Администратор смотрит запись журнала по пользователю/request ID и сверяет её с логами Postbox за `created_at`. Поля журнала: `state`, `provider_message_id`, `reason`, время, идентификаторы и SHA-256; исходный текст в БД не хранится. Технические ответы Postbox и секреты пользователю не показываются.

Если Postbox подтвердил принятие, администратор может вручную зафиксировать `accepted` с соответствующим `MessageId`; затем тот же запрос сохранит прогресс без отправки. Если достоверно подтверждено, что письмо **не было принято**, администратор может вручную пометить запись как `rejected` с `reason='provider'` и разрешить пользователю создать новую попытку. Это контролируемая операция с БД, не автоматический retry. При отсутствии доказательств запись оставляют заблокированной. Не удаляйте/не очищайте журнал как способ восстановления: это снимает защиту от дублей. Событие доставки само по себе не меняет факт принятия в журнале.

## Шаблон и проверки

`email-template.ts` содержит тему, исходное текстовое письмо и его минимальный HTML-эквивалент. Тексты, подпись и переносы сохранены. Дополнительного оформления, логотипа или изображений пока нет. Для последующей смены дизайна, цветов, текстов и изображений меняйте только этот файл. Весь пользовательский текст экранируется (`& < > " '`) перед подстановкой в HTML. Новых зависимостей для оформления нет. Шаблоны писем авторизации Supabase Auth не затрагиваются.

`postbox.ts` использует совместимый с Deno `aws4fetch@1.0.20` только для Signature V4 через `sign()`, затем единственный `fetch`. Встроенные повторные попытки `AwsClient.fetch()` не используются; дополнительно выставлено `retries: 0`. Зависимость закреплена в `deno.json`/`deno.lock`, а в npm devDependencies нужна для локальных mock-тестов и проверки типов, во фронтенд не импортируется.

```bash
npm ci
npm test -- tests/send-gratitude.test.ts tests/gratitude-sql.test.ts
npm test
npm run typecheck
deno check --config supabase/functions/send-gratitude/deno.json supabase/functions/send-gratitude/index.ts
npm run build
npm run test:e2e -- tests/tasks.spec.ts --grep gratitude
npm run test:e2e -- tests/auth-attachments.spec.ts --grep verification
```

Тесты подменяют все сетевые вызовы Auth/REST/Postbox и отдельно запрещают случайный реальный `fetch`. SQL-проверки используют локальный PostgreSQL через PGlite. Проверяются Signature V4 независимым расчётом HMAC, From/Reply-To, экранирование и анонимность, JWT и доступ, ограничения, повторы/параллельные запросы, потеря результата, квоты, таймаут, сбой журнала и повтор сохранения прогресса. Настоящие ключи, внешний Postbox и production БД не нужны.
